## 二、S1（用户能直接看到）

### I-01 线框「一个链一个颜色」
- **现象**：线框表示下整条链一个颜色，`md.gro`（溶剂盒子）里几乎全是一种颜色。
- **根因（三因叠加，见 PLAN §2）**：
  1. **R1 必键单端取色**（旧 `wireframe.cpp:48`）→ ✅ 已修（半键拆分 `wireframe.cpp:44-61`）；
  2. **R2 `Chain` 每链一常量色**（`representer.cpp:126-132`）→ 属设计，VMD 亦如此；
  3. **R3 GRO 链映射错误**（见 I-02）→ ❌ 未修，这是 `md.gro` 的真凶。
- **证据**：改动前 `_test\vmd\our_wireframe.png` 量化后仅 2 种颜色（O 红 93.7% / C 灰 6.3%，H 白底白线不可见）。
- **建议**：先做方案 B（线框默认 `AtomName`，约 10 行）止血，再做方案 A（表驱动链色板 + 链内 ±6% 亮度扰动 + Residue 按实例）。

### I-02 GRO 把残基名当链
- **位置**：`src/io/parser/gro/gro_parser.cpp:186-196`、`:311-312`。
- **现象**：`md.gro` 整个盒子只解析出 7 个"链"，`SOL` 一种颜色覆盖 **94.5%** 原子 → 视觉上就是"一整片同色"。
- **建议**：GRO 无真实链概念，应按分子序号/残基序号映射，或提供"按分子"配色维度；至少让 `SOL` 与溶质分层。

### I-03 `Residue` 配色按名字去重
- **现象**：同名残基（如大量 `SOL`）共享一色，与 VMD 的「逐 resid」语义不同。
- **建议**：改为按 (chain, resid) 实例算色；注意与 `selection.cpp` 的分组口径一致。

### I-05 `colorNames[5]` 越界读
- **位置**：`src/app/view/control/reps_tool.cpp:375-377`（活代码路径 `view_control.cpp:375` 实例化该面板）。
- **现象**：`ColorScheme` 已扩到 6 个值（新增 `AtomName`），但旧「图形表示」面板下拉仍是 5 项 → `colorIdx=5` 时越界读，可能崩溃或显示乱码。
- **建议**：下拉改用枚举驱动（`Count`/数组长度统一），并加静态断言；顺手补单测。

## 三、S2（体验 / 工具）

### I-04 配色名缺 `AtomName`
- `representer.cpp:36-45` 的 `colorSchemeZhImpl` 没覆盖 `AtomName` → 界面显示"未知"。加一行 case 即可。

### I-06 调色板 sRGB / 线性错配
- 附件是 `*_SRGB`，顶点色却按线性解释 → 颜色整体偏淡。实测 O = `(255,64,64)`，按 sRGB 编码反推应为 `(255,13,13)`；`encode(0.05)=63≈64`、`encode(0.56)=197≈200` 与像素吻合。
- `cmd.h:61` 关于"sRGB 预计算"的注释与实现相反。
- **建议**：单独一轮做（牵涉 15 张插图与冒烟阈值），不要和线框配色混在一起。

### I-07 线框默认配色
- `representation.h:50` 默认仍是 `ElementCPK`，`setType` 不随样式切配色 → "能选但默认不对"。方案 B 里一并解决。

### I-08 帧率被钉在 64 FPS
- **现象**：载入 `md.gro` 前稳定 **117 FPS（8.5 ms）**，载入后持续 **64 FPS（15.6 ms）**，且渲染工作量只占周期 **15–20%**（avg 2.4 ms）→ 瓶颈不在绘制，疑似 vsync / 帧节流 / 提交策略。
- **证据**：本轮 899 条 perf 采样：64 FPS 占 736 条，117–118 FPS 仅 53 条；切换点对应 12:16:18 表示从 sphere 切到 line。
- **13:38 新证据（很关键）**：同一份 Release 程序**空场景**跑出 **119 FPS（8.39 ms，工作量 0.57 ms）**；载入 `md.gro` 后立刻掉到 64 FPS。也就是说 64 FPS 是**载入场景后才出现的天花板**，不是显示器刷新率——更像"有大场景时启用了 vsync / 帧节流 / 每帧等待 GPU"。
- **建议**：查 swapchain present mode（MAILBOX/IMMEDIATE）、帧节流开关、"大场景自动降频"逻辑，以及是否每帧 `vkWaitForFences` 同步过强。


### I-09 偶发长帧

## 四、S3（噪声 / 环境坑 / 流程）

### I-11 SDF 版本警告
- `[io] SDF line 80: unsupported SDF/MOL version (only V2000 supported), record skipped: '> <PUBCHEM_COMPOUND_CID>'`
- 读 PubChem 导出的 SDF 时属性块被当成新记录 → 跳过。不影响主结构，但会让属性丢失。

### I-15 VMD 写 PNG 失败回落 BMP
- Tachyon/AO 渲染时 `ERROR) Unrecognized image file extension, writing Windows Bitmap file.` → `_test\vmd\vmd_ref_*.png` 实际是 BMP（文件头 `42 4D`），真 PNG 是 `*_conv.png`。
- 另：两次渲染用同一路径会得到字节完全相同的"假重复"（都是 1,890,054 B）。

### I-16 子会话 GUI 授权卡审批
- 授权按 **agent 会话**隔离：子会话调用 `request_access` 会一直等审批（本次实测卡 43 分钟）；GUI 操作应在有授权的主会话内做，或让主会话先批。

### 构建噪声（不算缺陷）
- `error MSB3073 ... 已退出，代码为 3`：构建后自定义命令（copy font / make_directory）的噪声，只要看到 `-> ...exe` 即成功。

### 日志路径会随启动目录变化（排查时容易踩）
- 程序把日志写在 **当前工作目录**下的 `logs\moleculens.log`。所以同一个 exe 会有多份日志：
  - 从 CLion / `cmake-build-debug` 启动 → `cmake-build-debug\src\app\logs\moleculens.log`
  - 从仓库根启动 Release → `F:\MolecuLens\logs\moleculens.log`
  - 从 `build\src\app\Debug` 启动 → `build\src\app\Debug\logs\moleculens.log`
- **排查任何问题前，先确认哪份日志在涨**（看 mtime），否则会看成"日志停更 = 卡死"的假象（监控脚本就因为写死路径误报过一次 531 秒停更）。

## 七、环境坑：sandbox 授权没传播到旧子目录（2026-10-21 14:05 已修，记录成因）

**现象**：把本会话文件策略从「完全权限」切成 `workspace-write` 后，`F:\MolecuLens\` 根、`docs\`、`.monitor\` 可写，但 **`src\`、`build\`、`tests\`、`shaders\` 全部不可写**（`对路径 ... 的访问被拒绝`），导致会话无法改代码、构建失败。

**成因**：DSH 在工作区根加了一条可继承的沙箱授权条目
`S-1-4-632944777-794154334:(OI)(CI)(W,D,DC)`，但这四个目录是在该条目加入**之前**创建的，Windows 没有把继承 ACE 回填到既有子对象；`docs\`、`.monitor\` 是之后创建/改写的，所以有。

**官方诊断脚本**：`diagnose-windows-sandbox-acl` 在本机**跑不起来**——`Get-Acl` 模块加载失败
（`TypeData "System.Security.AccessControl.ObjectSecurity" ... 成员已存在`），换独立 `powershell.exe -NoProfile` 也一样，verdict 恒为 `UNREADABLE`，不修改任何东西。这是 PowerShell 类型数据冲突，不是权限本身的问题。

**修法（已验证）**：用 .NET 直接读根目录的 ACE，再把**同一条**规则加到四个子目录：

```powershell
$root = 'F:\MolecuLens'
$rootAcl = [IO.Directory]::GetAccessControl($root,'Access')
$ace = $rootAcl.Access | Where-Object { $_.IdentityReference.Value -like 'S-1-4-*' -and $_.AccessControlType -eq 'Allow' } | Select-Object -First 1
foreach ($d in 'src','build','tests','shaders') {
  $p = Join-Path $root $d
  $acl = [IO.Directory]::GetAccessControl($p,'Access')
  if ($acl.Access | Where-Object { $_.IdentityReference.Value -eq $ace.IdentityReference.Value -and -not $_.IsInherited }) { continue }
  $acl.AddAccessRule([System.Security.AccessControl.FileSystemAccessRule]::new($ace.IdentityReference,$ace.FileSystemRights,$ace.InheritanceFlags,$ace.PropagationFlags,'Allow'))
  [IO.Directory]::SetAccessControl($p,$acl)
}
```

**撤销**：`icacls <目录> /remove "*S-1-4-632944777-794154334" /T`（只删这一条授权，其它不动）。

**下次遇到同类症状**：先 `icacls <目录>` 对比根目录，看是否缺 `S-1-4-*` 那条；缺就按上面补，别先去怀疑代码。

## 十五、I-08 结案：64 FPS 天花板**无法复现**，实为 120 FPS 限帧器（17:55）

**实测（Debug 构建，md.gro 2042 分子 / 6452 原子）**

| 配置 | 窗口 | 整帧 | CPU 工作量 |
|---|---|---|---|
| 默认（msaa4 + vsync FIFO） | 1280×800 | **8.55 ms（117 FPS）** | 1.27 ms |
| msaa=1 | 1280×800 | 8.52 ms（117 FPS） | 1.25 ms |
| msaa=1 + 关 vsync（IMMEDIATE） | 1280×800 | 8.46 ms（118 FPS） | 1.47 ms |
| 默认 | **最大化 1366×768** | **8.49 ms（118 FPS）** | 1.50 ms |

**结论**
1. 载入 md.gro 后**稳定 117–118 FPS**，13:38 那次记录的 15.6 ms（64 FPS）在当前代码上**复现不出来**——大概率是旧构建或当时的窗口/表示状态不同；
2. **vsync 开/关、MSAA 4/1 都没有可测差异**（8.46–8.55 ms），说明帧率不是被呈现模式锁的；
3. 真正的上限是代码自己的**120 FPS 限帧器**：`view_control.cpp:547 kTargetFps = 120`，每帧睡到 8.33 ms 预算结束（`timeBeginPeriod(1)` + 1.2 ms 自旋收尾）。空场景 118 FPS 也是这个原因；
4. 顺带修掉一个**真 bug**：`Settings::msaa` 从来没被应用（`view_control.cpp` 写死 `cfg.msaaSamples = 4`），现在改为读设置，并支持 `MOLECULENS_MSAA` 环境变量覆盖。

**后续建议**
- 若用户仍感觉卡：先看窗口是否远大于 1366×768（填充率），或打开「SSAO/阴影/线框」等叠加物；
- 想要更高帧率：把限帧器做成设置项（`kTargetFps` 可配 60/120/144/不限），比关 vsync 更直接。

## 十九、v2.9 表示表格相关（2026-10-21 23:50）

**I-19 点击「新建」表示后进程崩溃 0xC0000005（已修复）**
- 现象：已有 1 个表示时点「新建」，日志连续 4 条 `event published: type=3` 后 `CRASH: code=0xC0000005`。
- 根因：`VisualizeModule::render()` 里 `const Representation& r = wb.representations()[static_cast<size_t>(id)];` 取的是 vector 内元素的**引用**；同一帧内 `ctl->addRepresentation()` 触发 vector 重新分配，`r` 立刻悬垂，后续 `r.visible / r.colorScheme / r.diffuse` 全读野内存。
- 修复：改为按值快照 `const Representation r = ...`（表示对象仅几个 vec4 + 字符串，每帧一份拷贝可忽略）。凡是在同一帧内可能增删表示的 UI 都要按值取。
- 教训：UI 代码里**凡是"先取引用、后可能改容器"的写法都要按值**；这类 bug 只在"添加第二个对象"时触发，单对象用例测不出来。

**I-20 ImGui 表格内行级 PushID 无效 → "2 visible items with conflicting ID"（已修复）**
- 现象：表示表格有 2 行以上时弹出 Dear ImGui 断言框，红框标出两行的名称/样式单元格。
- 根因：ImGui 的 `TableSetColumnIndex()` 内部用 `PushOverrideID(column->ID)` **替换** ID 栈顶，导致 `TableNextRow` 外层 `PushID(i)` 在单元格内不参与哈希 → 两行同名控件（如都叫「球棍」）算出同一个 ID。
- 修复：每个单元格控件自带行号后缀，如 `style + "##st" + std::to_string(i)`、`"##style_pop" + i`、`"...##rm" + i`；弹出菜单同理。
- 附带修复：行选中不再用 `ImGuiSelectableFlags_SpanAllColumns`（它与单元格内的 Selectable 重叠，也会触发 ID/命中异常），改为 `TableSetBgColor(ImGuiTableBgTarget_RowBg0, ...)` 给整行上底色。

**v2.9 表示表格最终形态**
